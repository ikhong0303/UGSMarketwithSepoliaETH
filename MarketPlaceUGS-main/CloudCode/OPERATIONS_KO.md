# 테스트 서버의 결제·거래 상태 확인

## 저장 구조

Cloud Save Game Data `simple_market`의 `state` 객체를 사용합니다.

- `payments[txHash]`: 지급 계정, 10,000골드, GRANTING / GRANTED, 시각
- `listings[listingId]`: 판매자, 원본 아이템 ID, 가격, CREATING / ACTIVE / BUYING / SOLD / CANCELLING / CANCELLED
- 판매 완료 매물의 `earningsStatus`: AVAILABLE / CLAIMING / CLAIMED
- `operations[gachaId]`: 가챠의 계정·추첨 결과, GRANTING / DONE

원래 제공된 `js/*.txt`의 `market/active_listings`와는 다른 저장 구조입니다. 자동 마이그레이션은 하지 않습니다. 새 테스트 UGS 프로젝트에서 새 스크립트 8개를 함께 배포합니다.

## 중복 지급 방지와 복구 한계

금전·아이템 변경 **전에** 기존 `state`의 writeLock으로 처리 권한을 예약합니다. 경쟁 요청 중 예약에 성공한 한 호출만 Economy 변경을 실행합니다. 중복된 결제 해시, 구매와 취소, 판매대금 수령의 동시 요청을 차단합니다.

하지만 Cloud Save와 Economy는 단일 데이터베이스 트랜잭션이 아닙니다. Economy 변경이 성공한 직후 응답이 유실되거나 프로세스가 종료되면, 서버가 성공 여부를 확정할 수 없습니다. 이 경우 진행 상태를 유지하고 재지급을 중단합니다. **완전 자동 exactly-once 처리나 모든 장애의 자동 복구를 보장하는 구현은 아닙니다.** 정상 결제와 조회 재시도는 자동으로 처리하며, 모호한 결과만 수동 확인합니다.

## REVIEW_REQUIRED / 오래 남은 진행 상태

1. 해당 게임의 변경 작업을 잠시 멈춥니다. 살아 있는 Cloud Code 호출이 종료될 시간을 확보합니다.
2. `state` 객체를 별도 파일로 백업합니다. 해당 거래·작업 ID를 기록합니다.
3. Sepolia 영수증과 Cloud Code 로그, UGS Economy 기록을 대조합니다. **현재 잔액 숫자 하나만 보고 지급 여부를 추정하지 마세요.** 그 뒤에 다른 구매나 가챠가 있었을 수 있습니다.
4. 이미 지급된 것이 확인되면 지급 함수를 다시 호출하지 않고 해당 상태만 완료로 표시합니다.
5. 미지급이 확실한 경우에만 관리자 권한으로 누락분을 한 번 지급하고 상태를 완료로 표시합니다. 구매 중단이라면 차감·아이템 생성·판매자 정산을 각각 확인하여 누락된 단계만 처리합니다.
6. 판단할 증거가 부족하면 진행 상태를 유지합니다. `state` 삭제, 결제 해시 삭제, 상태를 ACTIVE로 되돌린 뒤 재구매 같은 방식으로 해결하지 않습니다.

일반 플레이어에게 지급 재시도나 관리자 복구 API를 제공하지 않습니다. 이 테스트 버전에는 자동 정산 작업자·관리자용 복구 UI가 없습니다.

## 소규모 테스트 한도

공유 원장은 결제 + 가챠 + 매물 합계 500건까지만 새 작업을 허용합니다. 작은 테스트를 위해 UGS 설정 수를 줄인 구조입니다. 완료된 지급 기록도 중복 지급 방지에 필요하므로 삭제하지 않습니다. 한도에 도달하면 별도의 새 테스트 환경·프로젝트로 시작하거나 서버 저장 구조를 확장해야 합니다. 기존 사용자 데이터를 유지해야 하는 서비스에서 단순 초기화하지 마세요.

실서비스로 확장하려면 작업별 원장·계정별 잠금·보상 트랜잭션·재처리 작업자·운영 관측·확정성 정책을 설계해야 합니다. 이번 코드는 Sepolia 학습·기능 통합용입니다.
